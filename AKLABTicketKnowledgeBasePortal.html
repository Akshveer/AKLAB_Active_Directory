HD-001Account & Identity Management

Password Reset Request

Password reset

Purpose

The ticket register identifies a password-reset request. Use this guide when a domain user cannot authenticate because their password is forgotten or needs to be changed.

Recommended procedure

Confirm the requester’s identity using the organization’s approved process. Locate the correct user account in Active Directory Users and Computers (ADUC). Reset the password only after authorization; communicate the temporary password through an approved secure channel and require a change at next logon where appropriate.

Verification

Verify that the user can sign in and that the account is not locked or disabled. Never include a real password in a ticket, screenshot, or knowledge article.

HD-002File Shares & Permissions

Cannot Access Employees Shared Folder

Shared-folder access

Purpose

A user reports that the Employees shared folder cannot be opened.

Recommended procedure

Confirm the user, computer, share path, and exact error. Test name resolution and network reachability to the file server. Review both share permissions and NTFS permissions, then inspect the user’s effective access through group membership and inheritance. Apply only the minimum approved permission change.

Verification

Retest using the affected user account. Confirm authorized access works and that unrelated folders remain restricted. Do not grant broad access such as Everyone: Full Control as a workaround.

HD-004Security & Access Control

Unauthorized Shared Folder Access

Unauthorized access

Purpose

A user may have access to a folder that is outside their job responsibilities.

Recommended procedure

Identify the exact folder and user. Review share permissions, NTFS permissions, inherited entries, and security-group membership. Confirm the intended access model with the data owner before changing permissions.

Verification

Test as the affected user and, where possible, an authorized user. Confirm the unauthorized path is denied while legitimate access remains functional. Preserve evidence of the before-and-after permission review.

HD-005File Shares & Permissions

Unable to Access CompanyShare Network Location

Network share connectivity

Purpose

A workstation cannot reach the CompanyShare network location.

Recommended procedure

Confirm the UNC path, for example \\DC01\CompanyShare, and verify the client has the expected IP configuration and DNS server. Test server name resolution and connectivity. Check that the share exists and that the Server service and firewall configuration permit SMB access.

Verification

Open the UNC path from the client using the affected account. Distinguish a network/path problem from an authorization problem; do not change permissions unless evidence points to an access-control issue.

Repeated failed sign-ins

Purpose

Repeated authentication failures may trigger account lockout or indicate stale credentials.

Recommended procedure

Identify the account and time pattern. Check whether the user is entering an incorrect password or whether saved credentials, mapped drives, services, scheduled tasks, or other devices are retrying old credentials. Review relevant security events where available.

HD-022Backup & Recovery

Configure File Version History with Shadow Copies

Volume-level previous versions and recovery

Purpose

Provide authorized users with a practical way to inspect and recover earlier versions of shared files without immediately requiring an administrator-led restore.

Overview

Windows Server Shadow Copies can provide previous versions of files stored on a supported volume. Users with appropriate access can inspect available versions of shared files through the Previous Versions tab. Shadow Copies are volume-based and do not replace independent backups.

How to configure and use Previous Versions

On the file server, identify the volume that hosts the shared folder. Open the volume’s Properties, select Shadow Copies, and configure the feature, including an appropriate storage limit and snapshot schedule.

To inspect an earlier file version, open the shared file or its parent folder in File Explorer, select Properties → Previous Versions, and choose an available timestamp. Use Open or Copy to examine the content before selecting Restore, because restoring may overwrite the current version.

How to check

Confirm that the selected volume has available snapshots and that the Previous Versions tab lists the expected timestamps. If no version appears, check whether a snapshot existed before the file changed, whether the correct volume is configured, and whether the user can access the share.

Operational cautions

Shadow Copies are not an independent backup: snapshots on the same volume may be lost if the volume fails, storage pressure can purge old versions, and not every file change is captured. Preserve separate backup and restore procedures.

HD-023Backup & Recovery

Automate File Version History Snapshots

Scheduled Shadow Copy snapshots

Purpose

Reduce reliance on manual snapshots by scheduling recurring Shadow Copy creation for the shared-file volume.

Overview

Scheduled Shadow Copies create periodic recovery points for files on a selected volume. The appropriate frequency and storage quota depend on how often files change, available disk space, and recovery requirements.

How to schedule Shadow Copies

On the file server, open the relevant volume’s Properties → Shadow Copies → Settings → Schedule. Review existing entries, choose the required times and recurrence, and confirm that the schedule applies to the correct volume.

Check that the shadow-storage limit is appropriate and that the server clock and time zone are correct. Avoid creating overlapping or duplicate schedules.

How to check

After a scheduled time has passed, check whether a new snapshot was created automatically. Inspect a previous version of a non-sensitive file to confirm it can be opened. A manually created snapshot does not verify that scheduling works.

Troubleshooting

If no scheduled snapshot appears, review the configured schedule and selected volume, server time, free space and storage limit, and relevant Windows event logs. Check that Volume Shadow Copy Service dependencies are functioning. Avoid reducing the quota without assessing whether older snapshots may be deleted.

HD-024Group Policy & Security

Centralized IT Announcement System

JSON-driven logon announcements

Overview

A centralized IT announcement system can display non-confidential notices to domain users when they sign in. In this approach, a shared JSON file holds the notice, a PowerShell script displays it, and a Group Policy–deployed scheduled task starts the script after logon.

Components and access

The shared folder contains a JSON announcement file and the PowerShell display script. Domain users need read access to the files, while modification rights should be restricted to authorized IT administrators. Both share permissions and NTFS permissions affect access.

Each notice should have a unique AnnouncementID. A per-user record of previously displayed IDs can prevent the same notice from appearing repeatedly.

How announcements are managed

An authorized administrator updates the announcement title, message, and unique ID in the JSON file. The JSON field names must match those expected by the display script. A new ID allows the next notice to be shown even when a previous one has already been acknowledged.

Keep the notice appropriate for all users who can read the shared file, and protect the central script from unauthorized changes.

How delivery works

A Group Policy Preferences scheduled task can launch the PowerShell script in the interactive user session after logon. A short delay can allow network connectivity to become available before the script accesses the shared files.

The script reads the current announcement, compares its ID with the user’s local seen-announcement record, and displays the message when the ID is new. This method shows notices at sign-in rather than immediately pushing them to users already signed in.

Troubleshooting

If the notification does not appear, check whether Group Policy applied, whether the scheduled task exists, and whether it runs in the signed-in user’s interactive context. Confirm that the network share and script are readable and that the local seen-announcement file is writable.

For a Group Policy Preferences scheduled-task error such as 0x80070005 (Access is denied), inspect the task principal, permissions, and relevant Group Policy event logs. A successfully applied GPO does not by itself confirm that its scheduled task was created.

How to check

Sign in with a test domain account and allow the scheduled task to run. Confirm that a new notice appears, that the same announcement is not repeatedly displayed to that user, and that a different announcement ID produces a new notification on a later sign-in.

If several users are targeted, test with more than one account to check that per-user tracking works independently.

Important considerations

Use the system for non-sensitive notices only. Keep the JSON file and PowerShell script protected against unauthorized edits, and remember that users must be able to reach the shared location for the notification to load.

Useful checks

On a domain client, gpresult /r can help confirm applied Group Policy. Get-ScheduledTask -TaskName "AKLAB-IT-Announcement" can check whether the task exists. Test-Path "\\DC01\CompanyShare\IT-Announcements\Current-Announcement.json" can check access to the announcement file. Adapt names and paths to the environment.
